## P0-001 · Rate limiter y tres endpoints en 503

### Incidencia

La ejecución #76 falló 3 de 38 smoke checks:

- `POST /api/music/plan` → 503
- `POST /api/music/agents` → 503
- `POST /api/agent` → 503

Causa: `lib/rate-limit.ts` devolvía `unavailable` cuando faltaban
`KV_REST_API_URL`/`KV_REST_API_TOKEN`, y las rutas traducían ese estado a 503.
CI no tiene Redis, así que se castigaba a endpoints deterministas que no llaman
a ningún proveedor externo. Además `NODE_ENV=production` lo define `next start`
también en local y CI, por lo que no sirve como señal de producción real.

### Cambio

| Archivo | Cambio |
|---|---|
| `lib/rate-limit-engine.mjs` | Motor puro: resolución de modo, ventana deslizante en memoria, políticas por ámbito/costo, métricas |
| `lib/rate-limit-engine.d.mts` | Contrato tipado del motor |
| `lib/rate-limit.ts` | Adaptador Next/Redis, fallback controlado, logs estructurados, `checkPolicy`, `enforcePolicy`, `rateLimitSubject`, diagnóstico |
| `app/api/music/plan`, `music/agents`, `music/analyze`, `music/compose`, `music/search`, `tts`, `advanced-audio/exam`, `advanced-audio/evaluate` | Migradas a `enforcePolicy` con ámbito explícito |
| `app/api/agent/route.ts` | `checkPolicy` con ámbitos anónimo/autenticado; sin `ipOf`/`bucketKey` duplicados |
| `app/api/health/route.ts` | Estado operativo sin secretos: checks y modo del limitador |
| `scripts/test-rate-limit.mjs` | 15 pruebas unitarias |
| `scripts/test-rate-limit-http.mjs` | Cupo real 20/min, 429, cabeceras y los tres endpoints recuperados |
| `.github/workflows/ci.yml` | Ejecuta ambas pruebas y verifica `/api/health` |
| `.env.example`, `README.md`, `docs/PRODUCTION_BLOCKERS.md` | Documentación de variables, modos y fallo cerrado |

### Reglas de decisión

| Entorno | Backend | Resultado |
|---|---|---|
| Desarrollo, CI, Preview | memoria por proceso | aplica el cupo, no es global |
| Producción + `KV_REST_API_URL`/`KV_REST_API_TOKEN` | Redis distribuido | cupo global |
| Producción sin Redis | ninguna | 503 explícito, registrado |
| Producción sin Redis + `RATE_LIMIT_ALLOW_MEMORY_FALLBACK=true` | memoria degradada | emergencia declarada, registrada |

Producción se declara con `VERCEL_ENV=production` o
`PLAY_AND_GO_ENV=production`. Un fallo de Redis en producción devuelve 503; no
se interpreta como permiso. Las decisiones rechazadas incluyen
`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`,
`X-RateLimit-Mode` y `Retry-After`.

## P1 implementado en esta sesión (sin credenciales)

### P1-001 · Derechos transaccionales e idempotentes

- `supabase/migrations/20261111170000_transactional_fulfilment.sql`:
  `grant_product_entitlement` bloquea por usuario, registra la sesión de
  Checkout y delega el estado efectivo en `sync_entitlement_effective_state`.
- `lib/fulfilment.ts` sólo llama a la RPC; ya no hace lectura-cálculo-escritura.
- `scripts/verify-entitlement-lifecycle.mjs` pasa de 12 a 15 contratos e impide
  que vuelva el `upsert` directo.

Evidencia local:

```bash
node scripts/verify-entitlement-lifecycle.mjs   # 15/15 pass
node node_modules/typescript/bin/tsc --noEmit   # exit 0
```

Pendiente: aplicar la migración en staging/Postgres y probar dos webhooks
concurrentes de la misma sesión y de sesiones distintas. Sin base de datos real
no se puede afirmar que el bloqueo funcione en producción.

### P1-002 · Callbacks con expiración y nonce de un solo uso

- `lib/callback-signature-core.mjs` + `.d.mts`: firma
  `v1.<songId>.<exp>.<nonce>` con HMAC-SHA256, TTL de 24 h y verificación con
  motivos (`missing`, `malformed`, `expired`, `invalid`).
- `supabase/migrations/20261111180000_callback_replay_protection.sql`:
  `generation_callback_tickets` y consumo atómico del nonce.
- `/api/generate` emite `sig`, `exp` y `nonce`; `/api/generate/callback`
  consume el ticket después de aplicar un resultado terminal.
- `/api/callback` deriva la canción objetivo del `songId` firmado y no del
  `taskId` del cuerpo.
- Pruebas: `scripts/test-callback-signature.mjs` (7/7) y
  `scripts/verify-callback-security.mjs` (13/13), integradas en CI.

Evidencia local:

```bash
node --test scripts/test-callback-signature.mjs  # 7/7 pass
node scripts/verify-callback-security.mjs        # 13/13 pass
```

Pendiente: aplicar la migración y probar con el proveedor real callbacks
duplicados, expirados y manipulados. Los proveedores que sólo firman el cuerpo
no ofrecen expiración propia; esa limitación queda documentada.

### P1-003 · Contenedor real en la subida de audio

- `lib/audio-file-signature.mjs` + `.d.mts`: detecta WAV, OGG, M4A y MP3 por
  cabecera; `verifyAudioHeader` compara con el MIME declarado.
- `/api/songs/complete` lee 64 bytes antes de subir y responde 415 si el
  contenido no coincide.
- `scripts/test-audio-file-signature.mjs`: 6/6 pass.

Pendiente: archivos reales de cada proveedor, límite del bucket y validación de
duración en servidor (hoy la declara el cliente).

### P1-004 · Límites por cuenta en rutas autenticadas

Antes sólo tenían cupo las rutas públicas. Un usuario autenticado podía abrir
sesiones de Stripe, enviar exámenes, escribir progreso o subir audio sin techo.

- `checkout` 10/min (`external`), `exam.submit` 10/min (`local`),
  `progress.write` 30/min (`local`), `songs.complete` 12/min (`service`).
- Identifican por `userId`, no por IP: un aula con NAT compartido no se castiga.
- Conservan la regla de producción: sin Redis fallan cerrado con 503.

### P1-005 · Verificación estática de autenticación y aislamiento

`scripts/verify-auth-isolation.mjs` (12/12, integrado en CI) comprueba que:

- `/api/task/[taskId]` filtra por `provider_task_id` **y** `user_id`;
- la biblioteca y la subida usan `user.id` y la carpeta `<user_id>/` del bucket;
- el progreso pasa `p_owner: user.id` a la RPC y no lee un propietario del cuerpo;
- el plan se lee con `read_entitlement()` sin parámetros (ligada a `auth.uid()`);
- checkout, examen y evaluación exigen sesión y devuelven 401;
- ninguna ruta acepta `userId`/`user_id` desde el cuerpo o el query;
- RLS está activo en perfiles, canciones, derechos, progreso e insignias, con
  políticas que comparan contra `auth.uid()`;
- el bucket es privado y las cuatro operaciones de Storage exigen que la primera
  carpeta sea el `uid`;
- las rutas con `service_role` verifican Stripe o la firma del callback.

Es un contrato estático: no demuestra aislamiento en una base real. Esa prueba
sigue pendiente de staging con dos cuentas.
